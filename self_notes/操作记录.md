# 训练环境调试与问题解决详细记录

本文档详细记录了在尝试运行 TinyZero 训练脚本过程中遇到的一系列环境配置问题、调试步骤和解决方案。

---

## 阶段一：定位并解决 `libcuda.so` 链接失败问题

此阶段的核心是解决 `torch.compile` 在即时编译（JIT）CUDA 代码时，因找不到 NVIDIA 驱动的核心库 `libcuda.so` 而导致的训练失败。

### 1.1 初始错误

- **问题现象**: 运行训练脚本 `scripts/train_tiny_zero.sh` 后，程序在初始化模型时崩溃。
- **错误日志**: 关键错误信息为 `torch._dynamo.exc.BackendCompilerFailed: backend='inductor' raised...`，其根本原因是 C++ 编译器 (GCC) 在链接时报错 `ld: cannot find -lcuda`。
- **初步诊断**: 这表明虽然 PyTorch 运行时可以找到并使用 GPU，但编译器在编译新代码时，在其搜索路径中找不到 `libcuda.so` 文件。

### 1.2 寻找 `libcuda.so` 文件

为了让编译器找到该文件，我们首先需要在系统中定位它。

1.  **第一次尝试 (`find / -name libcuda.so`)**:
    *   **结果**: 找到了位于 `/usr/local/cuda-12.8/targets/x86_64-linux/lib/stubs/libcuda.so` 的文件。
    *   **分析**: `stubs` 目录下的文件是“桩库”，仅用于编译链接检查，不包含实际的驱动功能，因此不是我们需要的运行时库。

2.  **第二次尝试 (`find /usr/lib /usr/lib64 -name "libcuda.so*"`)**:
    *   **目的**: 将搜索范围缩小到最常见的系统标准库目录。
    *   **结果**: 成功找到以下文件：
        *   `/usr/lib/x86_64-linux-gnu/libcuda.so.1`
        *   `/usr/lib/x86_64-linux-gnu/libcuda.so.580.95.05`
    *   **分析**: 这确认了驱动库文件是存在的，位于 `/usr/lib/x86_64-linux-gnu/` 目录下。

### 1.3 修复链接错误的尝试过程

1.  **方案一：设置 `LD_LIBRARY_PATH` (失败)**
    *   **操作**: `export LD_LIBRARY_PATH=/usr/lib/x86_64-linux-gnu/:$LD_LIBRARY_PATH`
    *   **目的**: 将库所在的目录添加到动态链接器的搜索路径中。
    *   **结果**: 失败。错误依旧。
    *   **原因分析**: Ray 会为它的 `worker` 创建复杂的子进程环境，这个环境变量可能没有被正确地传递或继承到执行编译任务的确切进程中。

2.  **方案二：设置 `LD_PRELOAD` (失败)**
    *   **操作**: `export LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libcuda.so.1:$LD_PRELOAD`
    *   **目的**: 强制操作系统在加载其他库之前，首先加载 `libcuda.so.1`。这是一种更强力的注入方式。
    *   **结果**: 失败。错误依旧。

3.  **方案三：创建软链接 (成功)**
    *   **操作**: `sudo ln -s /usr/lib/x86_64-linux-gnu/libcuda.so.1 /usr/lib/x86_64-linux-gnu/libcuda.so`
    *   **诊断**: 仔细分析 GCC 的报错 `cannot find -lcuda`，它实际上是在寻找一个名为 `libcuda.so` 的文件 (`-l` 后面跟 `cuda`)。虽然系统中有 `libcuda.so.1`，但没有这个确切的文件名。
    *   **目的**: 创建一个标准的、无版本号的软链接 `libcuda.so`，指向实际的库文件 `libcuda.so.1`。这是 Linux 系统管理共享库的标准实践。
    *   **结果**: **成功！** 此操作之后，再次运行训练脚本，`cannot find -lcuda` 的链接错误消失。

## 阶段二：定位并解决 `CUDA out of memory` (OOM) 问题

链接问题解决后，训练进入了下一个阶段，但也暴露出了新的问题。

### 2.1 新的错误

- **问题现象**: 脚本成功启动，模型开始加载到 GPU，但很快就因 CUDA 内存耗尽而崩溃。
- **错误日志**: `torch.OutOfMemoryError: CUDA out of memory`。日志显示 GPU 0 的 24GB 显存几乎被完全占满。
- **诊断**: 默认的训练参数（如批处理大小）对于当前的模型规模和 GPU 配置来说过于激进，导致显存不足。

### 2.2 解决方案与代码修改

为了减少显存占用，我对训练脚本 `scripts/train_tiny_zero.sh` 进行了以下修改：

1.  **更新操作日志**: 将 OOM 问题及解决方案更新到 `self_notes/training_setup_log.md`。
2.  **修改训练参数**:
    *   将 `data.train_batch_size` 从 `256` 减小到 `128`。
    *   将 `actor_rollout_ref.actor.ppo_mini_batch_size` 从 `64` 减小到 `32`。
    *   为 Actor 模型启用了梯度检查点 (`actor_rollout_ref.model.enable_gradient_checkpointing=True`)，这是一种用计算时间换取显存空间的技术。
3.  **提交代码**: 这些修改已通过 Git 提交并推送到远程仓库。
    *   **Commit**: `feat: Reduce batch sizes and enable gradient checkpointing for OOM fix`

## 阶段三：调试脚本执行超时问题

应用了 OOM 修复后，出现了新的意外情况。

### 3.1 最新问题

- **问题现象**: 再次运行修改后的训练脚本，命令在执行 5 分钟后被自动取消，且**整个过程没有任何日志输出**。
- **诊断**: 这通常意味着两种可能：
    1.  脚本在执行的极早期（甚至在日志系统初始化之前）就因为某种错误而静默退出。
    2.  脚本卡在某个漫长的初始化步骤中，没有产生任何输出，最终导致看门狗超时。

### 3.2 调试步骤

- **操作**: 为了区分是脚本未执行还是执行后无输出，我在 `scripts/train_tiny_zero.sh` 的第一行添加了 `echo "Starting train_tiny_zero.sh script..."`。
- **目的**: 如果下次运行时能看到这条消息，说明脚本本身被成功调用，问题出在 Python 进程内部。如果连这条消息都看不到，则问题可能出在更上层的调用环境。

### 最终状态

会话在执行这个包含了 `echo` 语句的脚本之前结束。当前的主要阻塞点是解决这个“静默无输出”的超时问题。

## 阶段四：创建并优化训练启动脚本

为了提高训练命令的可维护性、可读性和易用性，我们将之前的长命令封装成一个新的 shell 脚本。

### 4.1 动机

之前用于启动训练的命令是一个包含多个 `export` 语句和 `bash scripts/train_tiny_zero.sh` 的长单行命令。这种形式虽然功能完整，但存在以下缺点：
- **可读性差**: 难以一眼看清所有配置和执行流程。
- **易用性差**: 每次执行都需要复制粘贴整个长命令，容易出错。
- **不易维护**: 修改任何一个环境变量或参数都需要重新构建整个命令字符串。

### 4.2 脚本创建

- **脚本名称**: `scripts/start_countdown_training.sh`
- **脚本内容**:
    *   加入了 `#!/bin/bash` 和 `set -e`，确保脚本在遇到错误时能及时退出。
    *   将所有核心训练参数（`N_GPUS`, `BASE_MODEL`, `DATA_DIR`, `ROLLOUT_TP_SIZE`）作为独立的 `export` 语句列出。
    *   清晰地列出了解决 CUDA 链接问题的环境变量（`LD_LIBRARY_PATH` 和 `LD_PRELOAD`），并附有注释解释其作用。
    *   通过 `echo` 语句增加了执行过程的反馈信息。
    *   最后一行调用了主训练脚本 `bash scripts/train_tiny_zero.sh`。
- **文件写入**: 使用 `write_file` 工具创建了该脚本文件。

### 4.3 脚本权限

- **操作**: `chmod +x scripts/start_countdown_training.sh`
- **目的**: 赋予新创建的脚本可执行权限，使其可以直接运行。

### 4.4 如何使用

现在，用户可以通过以下简洁的命令来启动训练过程：
```bash
./scripts/start_countdown_training.sh
```

这大大简化了训练的启动流程，并提高了命令的健壮性和可维护性。
